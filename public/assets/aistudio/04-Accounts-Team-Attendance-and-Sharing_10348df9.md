# Accounts, Team, Attendance and Share

## Account and profile

In the profile trigger and popup, use the current account’s portrait, display name, and smaller registered email on the next line. Use an accessible “Profile” label and an initials fallback. Keep existing Account Settings, theme, timezone shortcut within a project, and sign-out actions. Label the demo separately. Replace “Contractor Demo” as the identity heading. A daily selfie must never replace the account portrait.

Keep the registered email read-only in live and demo. Remove the new-address field, Save email and account email-change handler from the supported workflow. Restrict self-service email changes through the identity provider or trusted account policy too. Verify the actual provider configuration. A read-only input alone cannot enforce the rule. If the provider cannot enforce it in the current deployment, report the dependency. Preserve sign-in, verification and forgotten-password recovery.

For an authenticated password change, check the current password, check the new password and its confirmation, then send a one-time code or confirmation link to the account’s current verified email. Bind proof to this account, operation and expiry. Require successful proof before committing the new password. An already-recent sign-in, a notice after the change or a pending reset is insufficient. Keep the existing password usable until completion. Single-use proof, expiry, resend throttling, cancellation and failed delivery have distinct results. Do not log or persist password drafts in app storage. Keep the separate project-password flow. In demo, disclose that mail cannot be sent.

## Team

Move the destination to the project top bar and label it **Team**. Use the same header, clock and project context on demo and live paths. Center the page in the available column. Give the table full available width, stable row heights and a stable scroll region. Align names and roles for scanning; align percentages consistently. Align headers with cells. One result and fifty results use the same frame. Mobile users can scroll the table horizontally.

Above it, provide Department, Profession and Invite member. English role filters include Owner, Contractor, Architect, Foreman and Worker. Include Accounting when present so a real dedicated account remains discoverable. Use the current project role in the roster and identify a dedicated account type explicitly in the invitation confirmation.

| Exactly four visible data columns | Definition |
| --- | --- |
| Name | Current member display name. Keep row identity tied to the membership ID. |
| Role | Effective English project role. Eligible managers may change eligible assignments between Worker and Foreman using an inline menu. |
| Project tenure | Time since the effective project join date. Include the date in the accessible description. |
| Attendance % | Present / (Present + Alfa) for eligible finalized worker-days in the displayed reporting period. Display the period. Show an em dash for an exempt Owner or unavailable denominator. |

Owner, Contractor and Architect can change a current standard Worker to Foreman and back within their project. They cannot promote someone into a dedicated role, demote an incumbent dedicated role, or change global account type through this table. Place no permission/grant columns here. Preserve existing independent Workspace download and share entitlements. Foreman may edit authorized on-site Pins, create a material order/request for that exact Pin, and view applicable Store Requests and Purchase Requests. Creating or viewing a request does not approve spending or receive stock. Keep those decisions with their existing authorized actors. Foreman approval of leave remains team- and division-scoped.

## One invitation flow from Team and Share

1. An authorized project inviter enters the full email. Reuse existing invitation authority; the proposed default for this feature is Owner, Contractor or Architect within the active project. Recheck current authorization on the server. An anonymous viewer cannot search accounts.
2. Perform a server-side, exact normalized lookup against registered accounts. Return only what the inviter needs to confirm the registered type. A result might read “This account is registered as Owner.” Show “Account not registered” when absent and offer to check another address. No bulk directory or prefix search. Rate-limit and audit authorized lookups without exposing email lists, tokens or provider secrets.
3. Show registered type and proposed target-project assignment as separate fields. For a registered standard worker account, the inviter must explicitly select Worker or Foreman and confirm after seeing the result. For a registered Owner, Contractor, Architect or Accounting account, show its dedicated role as locked. Admit it with that exact role after acceptance. For an existing target-project member show their existing membership. Protect a dedicated role already present in that project. Preserve this role across projects. Do not offer a Worker/Foreman downgrade for a dedicated account.
4. Create one pending invitation for the exact project and recipient. Send email through the existing trusted delivery service. Let the recipient sign in with the matching verified identity and accept the invitation before membership becomes active. Handle mismatched accounts, expired/revoked invitations, duplicate clicks and resend. A send failure must not create a second invitation or active membership.
5. Recheck inviter authority, target identity and eligible assignment at commit/acceptance. Preserve unrelated project assignments. After acceptance, list the project in the recipient’s directory. Members cannot discover or self-join another project. Invitation grants the verified dedicated role or the confirmed standard Worker/Foreman role. It never changes the permission on a shared link.

## Attendance management

Provide two clearly labeled views, **Manual attendance** and **Attendance roster**. Keep calendar date and department filters in both. Show local project time. Remove the user-facing synthetic clock and time-edit controls. The project setup defines the timezone and scheduled start; the project clock alone is insufficient to infer a shift. Keep test-clock injection confined to tests.

**Manual attendance.** Put a camera preview on the left with Capture, Retake and Confirm. Put the worker ID field immediately below it. Put Search worker on the right. Search results show name, ID and a circular daily-selfie slot for the selected day. Until a valid capture exists the slot is empty. Authorized staff select a worker or enter their ID, verify the displayed subject, capture a fresh face selfie, and submit once. Ordinary workers can submit only for themselves. Recording for another worker uses the existing assigned-team/division authority or an explicitly existing HR attendance authority. HR visibility alone cannot grant review rights. Show the subject prominently before saving. Stop camera tracks when the view closes. Offer a retry for denied permission, missing camera or interrupted upload. A failed capture or upload cannot record Present. Do not introduce facial recognition or an automatic claim of on-site location.

**Attendance roster.** Put Search workers, calendar date and department above the roster. Show the selected date’s circular selfie, name, worker ID, effective status (Present, Izin, Alfa or awaiting check-in), attendance %, count of approved Izin, count of Alfa and an authorized link to leave evidence. Define counts/rate for the selected reporting period; the daily photo and day status are always for the selected work date. An explicitly identified Owner may appear with identity and em dashes in all attendance fields and is excluded from schedules, auto-Alfa and denominators. Keep the list of authorized team members visible even when no one has checked in. Workers see only permitted records. Full roster or HR access is a project entitlement.

**Izin and correction.** Accept a private evidence file from the worker, including the existing image formats and PDF supporting documents. Require a reason and at least one validated file. Bind objects to worker, project and obligation. Approve or reject directly on the roster, only as the eligible assigned Foreman. Require a rejection reason and prevent self-review. A pending submission does not change effective attendance. Separate request status from daily status. A private document link requires an independent current permission check. The daily photo stays empty for an excused worker who did not check in; an absence of a photo alone does not prove Alfa.

**Cutoff.** For eligible scheduled non-Owners, a complete trusted receipt before start + 3,600 seconds can count as Present. Exactly at the cutoff, no accepted check-in and no approved leave gives Alfa, even if all clients are closed. A later self-check-in cannot silently undo Alfa. Manual management can correct Alfa to Present with validated daily evidence and a reason, or record a justified Alfa correction, using existing scoped authority. Changing Alfa to Izin requires evidence and Foreman approval. Keep actor, subject, former result, reason, source and timestamps. Preserve original cutoff and work date. Handle races and retries once. Never modify the clock to achieve a correction.

## Share and download

The creator selects **Restricted** (default) or **Anyone with the link**. Both show the fixed permission **Viewer**. Keep the existing independent entitlements to create shares and download the clean PNG, including both for the active Owner and Contractor. A Share form may expose Invite to project only to an authorized inviter. This is independent of a viewer link.

| Mode | Who opens it | What is delivered |
| --- | --- | --- |
| Restricted | Signed-in recipient with active project and referenced model/area read access. Recheck on each open. | Dedicated read-only scene for the allowed model/version and permitted view state. |
| Anyone with the link | Any bearer of an active opaque link, including a signed-out visitor. Creation requires an authorized project member's explicit choice. | A dedicated viewer with an allowlisted model-view payload, approved for this share. Exclude original source files, raw project APIs, editing commands, team/attendance, budgets, private annotations, and internal Pin details or assignee data. |
| Invite to project | A registered person with a verified email accepts a separate scoped invitation. | Membership grants the existing dedicated role for a dedicated account, or Worker/Foreman for a standard account. Opening the original shared URL remains viewer-only, even for a member with editor rights. |

Check the target project, approved version and permitted fields when issuing a public reference. Resolve the bearer reference on a narrow server endpoint backed by private storage. Use an opaque high-entropy token with revocation; store a digest when practical and keep tokens out of logs. Provide change-to-restricted and Disable link. Invalidate old public access on restriction, revocation, or source withdrawal, including cached responses and long-lived asset URLs. Do not expose private model/source data to anonymous clients through a broad read policy. If the current deployment lacks this path, keep public creation unavailable with a clear reason until it is implemented and verified. Public sharing must not silently fall back to an editable workspace.

Show Copy link and supported native sharing. Preserve clean PNG and original permissions. Device drawings, rulers, wall fill, leave files and daily selfies stay out of all outputs. A recipient can orbit/zoom the allowed read-only scene. Public view gives no application-level download/export grant. As with any displayed content, a browser can display or capture the rendered view.
